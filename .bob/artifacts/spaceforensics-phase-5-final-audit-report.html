7. Technical Debt

TD-1  LOW
Case CSV discovery is synchronous. parseEvidenceCSV uses readdirSync inside an async function to locate the evidence file. For a single-case deployment at current scale this is immaterial (<1 ms), but it blocks the event loop during file-system access. If a second case is onboarded with a large CSV or if the endpoint is hit at high concurrency, this will become visible. Remediation: replace with fs.promises.readdir.
TD-2  LOW
POST /investigate and POST /challenge endpoints are not HTTP-integration-tested. Their logic is exercised by aiEngine.test.js at the unit level, but no test makes a supertest HTTP request to either route. Unknown-case 404 paths on these endpoints are untested.
TD-3  LOW
GET /api/cases/:id/evidence/:id/provenance has no HTTP integration test. The underlying function getEvidenceProvenance is tested (F18–F24), but the Express route handler itself — including its error handling — has no supertest coverage.
TD-4  LOW
Five frontend components have no render tests: App.jsx, Header.jsx, HypothesisMatrix.jsx, EventTimeline.jsx, RedTeamPanel.jsx, ReportModal.jsx. These are data-display components and do not implement forensic logic, but a rendering regression would be invisible to the test suite.
TD-5  LOW
No LLM-path HTTP integration test. All LLM-path tests inject a factory via the internal _llmFactory parameter of generateAnalystNarrative. The HTTP route calls aiAnalyst.generateAnalystNarrative directly without the injection parameter exposed to callers. A live-LLM HTTP integration test would require a Watsonx credential, which is intentionally absent in CI.
TD-6  MEDIUM
±10-minute temporal window is a hard-coded, uncalibrated heuristic. The code explicitly labels this: "this is an evidence-selection heuristic, not a scientifically calibrated causal threshold." The window value (600 000 ms) lives in server.js as an inline numeric literal with no named constant or configuration surface. If a second case with a different orbital period or anomaly duration is onboarded, the same window may misclassify evidence.

8. Scientific Limitations

The following limitations are explicitly encoded in the pipeline and surface in every API response under report.limitations and per-hypothesis limitations[]. They are not test failures — they are accurate descriptions of the dataset's scientific bounds.

SL-1  PROXY MEASUREMENT
GOES-11 EP8 and MAG measurements were recorded at a spacecraft approximately 2° of longitude from Galaxy 15. They characterise the near-GEO environment, not the in-situ environment at the anomaly satellite. This limits causal inference from any hypothesis that depends on local charged-particle flux.
SL-2  HEURISTIC WINDOW
Evidence selection for H1 (ESD) and H2 (SEU/SEE) uses a ±10-minute temporal window around the anomaly anchor. This is an investigative heuristic with no scientific calibration. Records outside the window are not analysed, and records inside it are not confirmed as causally related.
SL-3  CAUSAL ATTRIBUTION
causal_attribution_established = false for Galaxy 15 in every pipeline output. No hypothesis is proven causal by this dataset. The strongest assessment (H5 = strongly_supported) reflects consistency with available observations, not causal confirmation.
SL-4  MISSING DATA — H4
Hypothesis H4 (ground-station interference) has zero evidence records. No ground-station telemetry or RF monitoring data is present in the dataset. The insufficient_evidence assessment is correct and expected, not a pipeline defect.
SL-5  ENVIRONMENTAL CONTEXT ≠ CAUSE
GOES-11 EP8 and MAG records that fall within the heuristic window are classified as environmental_context for H1 and H2 respectively. They describe what the environment was at the time of the anomaly — they do not confirm that any specific mechanism occurred. This distinction is enforced at every layer: graph construction, forensic analysis, AI validator (B2), and UI labelling.

9. Remaining Risks

RK-1  MEDIUM
Second-case onboarding is untested. The readdirSync resolution mechanism (Phase 5.1) is verified to reject unknown cases and to return the correct Galaxy 15 dataset. However, no second case directory has been created. The mechanism has not been exercised with a real second case, only with the absence of a case (reject path). A second case with different evidence counts, different ID prefixes, or a different CSV column schema could reveal assumptions not yet tested.
RK-2  LOW–MEDIUM
Live LLM path is not integration-tested end-to-end. When a Watsonx API key is present, the HTTP handler calls the real LLM. The validator (A1–A10, B1–B4) provides a strong safety net, but the validator's behaviour when the LLM produces an edge-case response format not yet seen in tests (e.g., partial JSON, Unicode BOM, trailing whitespace after fence) is not fully exercised. The markdown-fence stripping test (LLM-10) covers one such case.
RK-3  LOW
No concurrency or load test. The pipeline is synchronous inside async routes. Under concurrent requests the synchronous blocks (buildEvidenceGraph, buildForensicAnalysis) will compete for the single Node.js event loop. No load test has been run to characterise degradation.
RK-4  LOW
Temporal window hard-coded as inline literal. The value 600 000 ms is written directly in the case function body in server.js with no named constant. A future developer who changes it without understanding the scientific implications could silently alter which evidence records are included in H1/H2 environmental context, affecting assessments.
