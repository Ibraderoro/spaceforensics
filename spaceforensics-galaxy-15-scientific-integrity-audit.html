CRITICAL C2 Confidence integers presented as sortable scientific scores without statistical basis
Filebackend/services/aiEngine.js lines 173–183, 280, 297, 312, 327 · frontend/src/components/HypothesisMatrix.jsx line 259 · frontend/src/components/ReportModal.jsx line 38 · frontend/src/App.jsx line 45
ProblemThe heuristic fallback assigns esdScore starting at 60, then adds 15 if ≥5 elevated flux rows, adds 10 if peak >2000, adds 5 if spike >500. seuScore starts at 50 and adds 10/5 for similar counts. These arbitrary additive integers are stored as confidence and directly drive hypothesis sort order in the UI and report. The LLM path maps categorical assessments back to integers (85/72/55/45/25) with equal arbitrariness. Pass 2 further adjusts by −15/−10/−5 per severity. None of these numbers have a statistical derivation, calibration dataset, or uncertainty bound.
Why it mattersPresenting an integer like "85" to a user implies probabilistic precision that does not exist. The UI and report sort and rank hypotheses by these numbers, creating an authoritative-looking ordering from what are purely arbitrary additive heuristics. This is the most direct mechanism for false scientific precision in the system.
Recommended fixRemove confidence from the heuristic output entirely. Sort hypotheses by categorical assessment using a defined ordinal mapping (e.g. strongly_supported > supported > mixed > weakly_supported > insufficient_evidence). Remove all integer arithmetic from Pass 2 score adjustment. The UI should sort by assessment tier, not a number. Any retained integer field must be labelled explicitly as "heuristic ordering index — not a probability."

HIGH H5 HW-C1 claim states "physical hardware destruction is ruled out" — this is a causal-certainty overstatement
Filebackend/services/aiEngine.js lines 258–263
ProblemClaim HW-C1 reasoning states: "Physical hardware destruction is ruled out by the autonomous reboot." This is deterministic causal language for what is an inference. The autonomous recovery demonstrates that a full power cycle or watchdog reset could restore nominal command processing — but this is consistent with multiple failure modes (latch-up recovery, firmware corruption, power anomaly). It does not rule out partial hardware degradation. Additionally, the claim uncertainty is set to 'observed' when the inference that the recovery "rules out" destruction is clearly 'inferred'.
Why it mattersThe CAUSAL_CERTAINTY_PHRASES list in aiEngine.js line 446 contains "Physical hardware destruction is ruled out" — but only checks LLM outputs through validatePass1Response. The hardcoded heuristic bypasses this validator entirely, so this phrase appears in final API responses unchecked.
Recommended fixRewrite reasoning to: "Autonomous recovery is inconsistent with permanent physical hardware destruction; however, it does not rule out transient hardware failure, latch-up, or firmware corruption." Change uncertainty from 'observed' to 'inferred'. The relationship should be 'non_discriminating' (not 'contradicts') for the hardware failure hypothesis.

MEDIUM M1 ELEVATED_FLUX_THRESHOLD = 1000 is an arbitrary constant presented as a scientific threshold
Filebackend/services/aiEngine.js line 30 · referenced in claim text at line 196
ProblemThe 1000 p/cm²/s/sr threshold is used to count "elevated flux readings" which directly drives the esdScore computation (+15 if ≥5 readings above threshold). This value has no documented derivation from spacecraft charging standards (e.g. ECSS-E-ST-20-06 or MIL-HDBK-1541). It is not cross-referenced to any published spacecraft charging threshold for the Star-2 bus.
Why it mattersUsing an uncalibrated threshold to count "elevated" flux readings and then using those counts to increment a score that produces a hypothesis ranking gives the appearance of a scientific criterion where there is none.
Recommended fixDocument the threshold as an MVP heuristic (add a comment like // HEURISTIC: no published spacecraft-specific charging threshold; this value is an analysis convention). In claim text, replace "> 1000 p/cm²/s/sr" with "above the heuristic investigation threshold" and surface the threshold value and its non-calibrated status in the claim's reasoning field.
MEDIUM M2 SEU-C3 claim: "Transponders remained operational" used to contradict SEU — this is an inference, not an observation
Filebackend/services/aiEngine.js lines 243–251
ProblemClaim SEU-C3 cites the CASE anchor event (which documents "transponders active") to contradict SEU. The reasoning says "A total SEU of the command processor would typically propagate to additional subsystems." The word "typically" is an unjustified engineering assumption not derived from any cited literature or dataset. It also conflates "total SEU" with all forms of SEU — a single-register upset in the command decoder would not be expected to propagate to the transmitter chain.

MEDIUM M4 B_GSM is stored as a scalar (|B|) but the variable in case.json implies a vector measurement
Filecases/galaxy-15/case.json lines 41–43 · fetch_galaxy15.py lines 54–55
ProblemThe fetch script computes |B| (L2 norm of Bx, By, Bz) and stores a scalar. The measurement name b_gsm and variable name B_GSM / B_GSM_c both imply a vector in GSM coordinates. The individual components (relevant for determining field orientation, which affects particle access and spacecraft charging geometry) are discarded. This is not disclosed in case.json's scientific_limitations.
Why it mattersA forensic analyst reading the evidence CSV would assume they are looking at a vector field magnitude that preserves directional information. The loss of Bx/By/Bz means that key physical quantities (e.g., Bz < 0 conditions that enhance geomagnetic storm access to GEO) cannot be reconstructed from the stored evidence.
Recommended fixAdd to scientific_limitations: "Only the total field magnitude |B| is stored; individual GSM components Bx, By, Bz were discarded during normalisation. Southward Bz conditions (relevant to geomagnetic storm enhancement) cannot be assessed from this data." Change the measurement name to b_magnitude or b_gsm_total.

Cross-Cutting Observations

Positive findings: The following areas were audited and found to be scientifically sound:

  • case.json → causal_attribution correctly states attribution is not established (line 5).
  • scientific_limitations array in case.json explicitly discloses proxy measurement distance (~2° separation), 5-min averaging, absence of Galaxy 15 magnetometer, and fill-value handling.
  • The CAUSAL_CERTAINTY_PHRASES validator in aiEngine.js is well-designed and covers the most common over-claim patterns.
  • Evidence IDs are deterministically assigned and traceable via the evidence_id → CSV row link.
  • Fill-value exclusion (FILL_ABS_THRESHOLD) is correctly applied; no −1E31 sentinels appear in the normalised CSV.
  • H3 (command-chain fault) and H4 (ground-segment) are appropriately represented in the evidence graph with insufficient_evidence assessments and missing-data limitations.
  • All test suites correctly verify provenance round-tripping, hallucination rejection, and evidence ID uniqueness.
  • Proxy-vs-direct measurement distinction is clearly labelled in limitations and claim reasoning throughout.

Architecture gap: The validatePass1Response / validatePass2Response validators are applied only to LLM output. The deterministic heuristic path is not passed through the same validators, meaning causal-certainty phrases and vocabulary violations in heuristic output are never caught at runtime (issues H5, H7).
